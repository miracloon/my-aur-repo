# pacman 仓库发布

> 使用同一公开 GitHub 仓库的固定 Release 交付 pacman 数据库和 x86_64 二进制包。

## 设计意图

### 单仓库、双存储面

GitHub 仓库本身保存可审计文本；同仓库 Release Assets 保存大型、可删除的交付物。二者共享项目与权限边界，但二进制不会进入 Git 对象和历史。

项目采用公开读取，因为配方与可再分发上游资产没有保密需求，并且 pacman 可以直接通过 HTTPS 消费，无需 Token、SSH 密钥或客户端同步脚本。

### 有界保留

数据库只提供当前版本，额外保留上一个包文件用于紧急手工回退。项目不承担历史版本归档义务；更旧资产自动清理。

### 签名边界

初始交付信任 GitHub HTTPS、仓库权限和 Actions。GPG 是可选的后续防御层，不是当前机制的前置条件，也不能在未实现时作为安全承诺。

## 结构与边界

### 固定发布入口

正式仓库使用与架构绑定的固定 Release tag，规范名称为：

```text
repository-x86_64
```

Release Assets 至少包含：

```text
my-aur.db
my-aur.files
<pkgname>-<pkgver>-<pkgrel>-<arch>.pkg.tar.zst
```

数据库文件必须以 pacman 请求的稳定名称发布。压缩实现后缀属于内容格式，不得迫使客户端改变仓库名。

### 资产归属

| 内容 | 位置 |
|---|---|
| PKGBUILD、声明、工作流和文档 | Git |
| 当前及上一个 Arch 包 | 固定 Release Assets |
| `my-aur.db`、`my-aur.files` | 固定 Release Assets |
| 下载源、构建目录和临时数据库 | Actions 临时环境 |
| 密钥和令牌 | GitHub Secrets 或 GitHub 内建 Token，不进入资产 |

### 客户端契约

客户端定义名为 `[my-aur]` 的同步仓库，Server 基址指向固定 Release。客户端架构为 `x86_64`，只需公开 HTTPS，不需要 GitHub 身份凭据。

`yay` 发现该同步数据库中的包时走 pacman 路径；只有同步数据库中不存在的包才会继续按其 AUR 行为处理。

### 再分发准入

进入公开 Release 的包必须具有可公开再分发依据。包声明或 PKGBUILD 应保留许可证和准确上游来源；不允许再分发的资产不能通过“自用”理由进入公开端点。

## 运转位置

### 发布前状态

publisher 接收已经验证且其 Git 文本状态已提交的包。它读取现有数据库与 Release 资产，形成新的当前包集合和需要保留的上一版本集合。

### 更新顺序

1. 获取单一发布写锁，避免并发修改数据库；
2. 上传新的包文件；
3. 验证新资产能够读取；
4. 使用标准 Arch 仓库工具生成或更新数据库；
5. 最后替换 `my-aur.db` 与 `my-aur.files`；
6. 数据库成功后清理超出保留窗口的旧包；
7. 释放发布锁。

先包后数据库保证新数据库不会引用尚未存在的包。GitHub Release 资产替换不提供严格的目录级原子性，数据库更新瞬间可能短暂不可用；客户端重试即可，发布流程不得将短暂不可用掩饰为原子事务。

### 版本保留

- 数据库每个 `pkgname` 只索引最高的当前版本。
- Release 每个包保留当前版本和紧邻的上一版本文件。
- 上一版本不在数据库中，只用于明确的手工回退。
- 清理失败不影响新版本可用性，但必须进入发布摘要。

### 发布恢复

Git 已提交而 Release 更新失败时，旧数据库保持为实际状态。后续运行比较 PKGBUILD 与数据库版本并重试，不能通过重用旧完整版本覆盖资产。

## AI 注意事项

- 不把 `.pkg.tar.zst` 或数据库提交进 Git，即使它们与仓库同名。
- 不在上传新包之前发布引用它的新数据库。
- 不让多个包构建任务直接修改 Release 数据库；只有 publisher 是写者。
- 不将公开 URL 等同于公开维护承诺。
- 不在未配置签名、客户端信任和失败恢复前把 `SigLevel` 提升为强制。
- 若未来引入私有资产，应增加独立交付通道，不把公开 Release 改造成需要客户端脚本认证的混合入口。
