# 包定义模型

> 用稳定的 pacman 包身份连接启用清单、上游监控声明与标准 PKGBUILD。

## 设计意图

### 包身份

- 一个 `packages/<pkgname>/` 对应一个 pacman 包身份。
- 包身份由交付内容决定，不由监控来源或资产格式决定。
- 上游 Release、tag、commit、deb、AppImage、tarball 或源码是策略属性，不形成目录分类。
- 上游交付方式变化时修改单包声明和 PKGBUILD，不搬迁包目录。

### 配置分工

| 载体 | 唯一职责 | 禁止承载 |
|---|---|---|
| `registry/packages.toml` | 包是否进入正式自动化 | 上游 URL、版本、依赖和打包步骤 |
| `package.toml` | 自动化无法从 PKGBUILD 得到的监控与资产选择信息 | 完整包元数据、启用状态、打包脚本 |
| `PKGBUILD` | Arch 包名、版本、依赖、来源、校验和及打包函数 | 调度、Release 发布、跨包状态 |
| `files/` | 必须自行维护的小型静态辅助文件 | 可在线固定获取的上游资产、构建产物 |
| 单包 `README.md` | 持续影响该包维护的特殊知识 | 当前失败、执行日志、项目级规则 |

同一事实只能有一个可修改来源。必要的跨载体一致性由验证器检查，而不是允许多份配置独立漂移。

### 版本身份

- 上游稳定版本规范化为 Arch `pkgver`；常见的前导 `v` 只在版本规范化时移除。
- 新上游版本令 `pkgrel` 回到 `1`。
- 仅打包内容变化时增加 `pkgrel`，表达本仓修订而不是伪造上游版本。
- 完整版本必须通过 Arch 版本比较严格高于已发布版本。
- 同一完整版本不可重用，即使旧资产已经删除。

后续监控 tag 或 commit 时可以采用不同的上游身份解析方式，但最终仍必须得到单调递增的 Arch 包版本。

### 架构与依赖

- 项目全局目标为 `x86_64`；不要求单包重复声明默认架构。
- 确实与架构无关的包可以在 PKGBUILD 中使用 `any`，但仍由同一 x86_64 仓库交付。
- 单包只选择本项目实际使用的上游资产，不维护上游完整平台矩阵。
- `depends`、`makedepends` 和 `checkdepends` 必须能够从 Arch 官方仓库或本项目已发布仓库解析。
- 只存在于 AUR 的必要依赖必须先作为独立包接入并进入清单，不能在构建时隐式下载。

### 封装边界

- 上游功能属于上游：本项目只保证它在 Arch 上以原样出现，不保证它的功能表现。
- 因此可用性不依赖逐项验证上游功能，只依赖三个事实：进包文件是上游资产里的原件、安装方位符合上游的路径假设、动态依赖不欠账。
- 路径映射是唯一允许的变换，且必须显式可读；为了"让构建通过"而 patch、strip、裁剪或改写资源，就越过了封装边界。
- 有意偏差与已知限制登记在单包 README，使"限制属于上游"可追溯。

## 结构与边界

### 单包最小结构

```text
packages/<pkgname>/
├── package.toml
└── PKGBUILD
```

`files/` 和 README 只有在存在真实内容时出现。`.SRCINFO`、`src/`、`pkg/` 和包文件始终是生成物。

### 声明约束

- 单包目录名、注册表键和 PKGBUILD 的 `pkgname` 必须一致。
- `package.toml` 必须声明 schema 版本和已注册的监控类型。
- 包名与全局架构不在 `package.toml` 重复保存。
- 资产选择只在上游存在多个候选且无法由 PKGBUILD 唯一表达时声明。
- 未知字段与无效组合是错误，不能静默忽略。

### 上游来源引用

- 上游 tag 写法和资产文件名属于上游习惯，不是配方知识：`my-aur prepare` 把已解析的 Release 身份写入 PKGBUILD 的 `_tag` 与 `_source_url`。
- 配方只引用这两个标量，本地来源文件名由本仓决定；上游更换 tag 前缀、资产名或打包格式时，只改 `package.toml` 的 `asset` 模式。
- 标量按需声明，避免无用字段；启用的包必须声明 `_source_url`，否则无法通过声明校验。

### 命名语义

| 包形态 | 命名 |
|---|---|
| 使用上游预编译产物 | `<name>-bin` |
| 使用稳定源码发布构建 | `<name>` |
| 直接跟踪版本控制 HEAD | `<name>-git` |

监控 GitHub Release 不必然使用 `-bin`；若 Release 提供的是源码并由本项目编译，包名仍为 `<name>`。

### 能力扩展

监控类型和资产选择属于受 schema 约束的注册能力。新增能力必须同时提供：

1. 明确的声明语义；
2. 公共实现；
3. 正常、无更新、异常输入和版本倒退测试；
4. 至少一个真实包的验证证据。

单包确有特殊打包需求时优先放在标准 PKGBUILD 中。只有跨包重复且属于自动化职责的逻辑才提升为公共能力。

## 运转位置

```text
registry 选择包
  → package.toml 告诉监控器如何得到上游身份
  → 自动化更新标准 PKGBUILD
  → makepkg 读取 PKGBUILD 生成 Arch 包
  → 验证器核对三个载体的一致性
  → pacman 数据库记录最终包版本
```

包定义模型连接监控与构建，但不负责工作流调度、故障 Issue 或 Release 资产更新。

---

## AI 注意事项

- 不从首个包复制字段形成所谓通用模板；先判断字段属于监控还是 PKGBUILD。
- 不为减少文件数量而把监控 API 调用写进 PKGBUILD。
- 不为追求抽象而把正常 PKGBUILD 函数改写成自有 DSL。
- 不登记维护者不使用的上游架构。
- 不通过 `SKIP`、隐式 AUR helper 或覆盖同版本资产来让构建勉强通过。
