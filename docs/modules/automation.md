# 自动化模块

> 在 GitHub Actions 中完成上游监控、配方更新、隔离构建、验证、提交、发布决策与故障交接。

## 内容索引

| 功能/领域 | 涉及栏目 | 一句话概要 |
|---|---|---|
| 触发与选包 | 设计意图、运转位置 | 每日、手工和 Push 共用一条执行主链 |
| 上游监控 | 结构与边界、运转位置 | 注册策略输出规范化版本身份 |
| 构建与验证 | 设计意图、结构与边界 | 每包隔离且公共门禁不可绕过 |
| 成功汇总与直接发布 | 运转位置 | 成功包继续，失败包不阻塞其他包 |
| 故障交接 | 结构与边界、运转位置 | 每包一个活动 Issue 供人或 AI 接手 |

---

## 设计意图

### 薄编排

自动化只连接 GitHub API、标准 Arch 工具和项目声明，不实现包管理器、依赖解析器或 PKGBUILD DSL。可测试的判断和数据变换属于 `automation/`，工作流 YAML 只负责权限、触发、任务编排和环境装配。

### 包级隔离

- 每个包在独立的一次性 Arch 环境中构建。
- 监控或构建失败只冻结对应包的发布状态。
- 成功包可以在同一轮继续提交和发布。
- 仓库数据库更新必须串行，不能沿用包级并发。

### 验证先于权限

AI 与工作流具有直接提交和发布权限，但只有通过公共门禁的结果才能使用这些权限。自用定位降低的是人工审批成本，不是验证要求。

## 结构与边界

### 自动化内部职责

公共实现允许按真实需要形成以下职责边界：

| 职责 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| registry | 根清单和包目录 | 启用且结构有效的包集合 | 查询上游 |
| monitor | `package.toml` 与上游元数据 | 规范化上游身份 | 修改 PKGBUILD |
| updater | 上游身份与 PKGBUILD | 候选文本变更 | 构建包 |
| builder | 单包目录与隔离环境 | `.pkg.tar.zst` | 修改 Release |
| validator | 声明、配方与产物 | 通过结果或结构化失败 | 放宽规则 |
| publisher | 成功包与现有仓库状态 | 新资产和数据库 | 构建失败包 |
| reporter | 失败结果 | 可更新的包级 Issue | 长期治理记录 |

这些是职责位置，不要求首次实现时机械建立同名空目录或类。

### 公共验证门禁

| 类别 | 最低检查 |
|---|---|
| 声明 | schema、未知字段、注册状态、目录与包名一致性 |
| 配方 | PKGBUILD 语法、来源校验和、版本与架构 |
| 构建 | 非 root、一次性 Arch 环境、只使用允许的依赖来源 |
| 产物 | 文件名、包元数据、`namcap`、禁止路径和动态依赖 |
| 安装 | 在新的干净环境中安装和卸载成功 |
| 版本 | 候选完整版本严格高于已发布版本 |

GUI 包不需要在无桌面 CI 中启动。包级检查只能增加门禁，不能关闭公共检查。

### 失败模型

失败结果至少包含包名、上游身份、当前已发布版本、失败阶段、简短错误和 Actions 运行链接。每个包最多有一个活动故障 Issue；重复失败更新原 Issue，恢复后关闭。

## 运转位置

### 触发

| 入口 | 选包范围 |
|---|---|
| 每日 schedule | 所有启用包 |
| workflow dispatch | 全部包或明确指定的单包 |
| 主分支 Push | 受影响包；公共逻辑变化时覆盖所有启用包 |

公开仓库的定时工作流可能因长期无仓库活动被停用。保活机制只在接近停用期限且没有正常提交时创建空提交，不修改文件或版本状态。

### 监控与准备

监控器读取声明并输出当前稳定上游身份。若其对应的期望包版本已经存在于 pacman 数据库，则停止该包；否则 updater 形成标准 PKGBUILD 变更并更新校验和。

监控类型只有在 schema、实现和测试同时存在时可用。稳定版过滤是默认行为，接入预发布版本需要新的明确治理决定。

### 构建与验证

候选包进入独立的官方 Arch `x86_64` 环境，由非 root 用户运行 makepkg。公共门禁完成后，各包结果汇总为成功集合和失败集合。

### 提交与发布

1. 仅提交成功包的文本变化；
2. 提交成功后把相应产物交给唯一发布任务；
3. 发布任务按仓库模块规则更新资产和数据库；
4. 发布失败时保留 Git 的期望版本，下一次依据数据库差异重试；
5. 失败包更新 Issue，成功恢复的包关闭 Issue。

---

## AI 注意事项

- 不把 Actions workflow 写成无法单元测试的业务脚本集合。
- 不因单包失败将整批标记为不可发布，也不让成功掩盖失败摘要。
- 不以 Git 中 `pkgver` 已更新为理由跳过对 pacman 数据库的实际状态检查。
- 不通过 `continue-on-error` 将验证失败伪装成成功；失败隔离应发生在包结果汇总层。
- 不在没有 schema、实现和测试时宣称支持新的监控类型。
