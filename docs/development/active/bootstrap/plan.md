# Bootstrap Plan

> Status: planned
> 本计划是当前 Design 的执行投影，可根据实现证据调整；它不证明任何能力已经存在。

## 阶段 1：建立仓库基础

**目标**：建立最小可验证的文本结构，不创建空壳能力。

- 初始化 Git 与基础忽略规则；
- 建立 `registry/packages.toml`、单包声明 schema 及验证入口；
- 选择公共自动化语言并配置对应环境；
- 建立最小 README，说明客户端目标与开发入口；
- 为配置解析、名称一致性和未知字段失败编写测试。

**完成证据**：结构验证和测试可运行，空清单与无效声明行为明确。

## 阶段 2：实现 Release 监控与版本准备

**目标**：只实现首个真实需要的 `github_release` 稳定版策略。

- 定义监控声明的最小字段；
- 查询最新稳定 Release 并规范化版本；
- 比较 PKGBUILD、上游和已发布数据库状态；
- 自动更新 `pkgver`、`pkgrel` 与来源校验和；
- 覆盖无更新、预发布过滤、版本倒退和 API 失败测试。

**完成证据**：固定输入测试与真实 MrRSS 元数据调查结果一致，且没有将其资产名写进公共监控逻辑。

## 阶段 3：接入 `mrrss-bin`

**目标**：形成完整、标准、可审计的单包定义。

- 核验最新稳定 Release 的 amd64 tar.gz、许可证和校验信息；
- 调查上游二进制在 Arch 中的实际动态依赖；
- 决定命令名、desktop、图标和许可证安装方式；
- 编写 `package.toml`、PKGBUILD 及必要辅助文件；
- 确认包版本关系和文件布局。

**完成证据**：单包目录不包含下载物，PKGBUILD 在远端干净环境中独立表达全部打包事实。

## 阶段 4：实现远端构建与公共门禁

**目标**：在一次性 Arch x86_64 环境中完成可重复构建和安装验证。

- 建立非 root makepkg 构建环境；
- 实现允许依赖来源检查；
- 实现 schema、配方、产物、namcap 和版本门禁；
- 在新的环境中安装和卸载包；
- 汇总成功与失败结果，不用 `continue-on-error` 掩盖失败。

**完成证据**：正式 Actions 运行成功；故意破坏校验和、版本和依赖时能在对应门禁失败。

## 阶段 5：实现固定 Release 仓库

**目标**：把验证后的包变成 pacman 可消费仓库。

- 建立 `repository-x86_64` 固定 Release；
- 使用标准工具生成 `my-aur.db` 与 `my-aur.files`；
- 串行执行包上传、可读性确认和数据库替换；
- 实现当前/上一版本保留与旧资产清理；
- 验证 Git 已提交但发布失败后的可重试性。

**完成证据**：Release 数据库只索引当前版本，且不会引用尚未存在的包资产。

## 阶段 6：接入触发与故障交接

**目标**：完成无人值守的日常运转面。

- 配置每日 schedule、指定包的 workflow dispatch 和路径感知 Push；
- 设置监控与发布并发边界；
- 实现每包一个活动失败 Issue 及恢复关闭；
- 增加低频空提交保活，避免公开仓库 schedule 因长期无活动停用。

**完成证据**：重复失败不制造 Issue 噪声，恢复能关闭 Issue，并发运行不能同时写数据库。

## 阶段 7：客户端验收与收束

**目标**：验证最终用户心智，而不是只验证 CI 产物存在。

- 编写客户端源配置与首次信任说明；
- 刷新数据库并通过 pacman/yay 安装 `mrrss-bin`；
- 验证再次运行无更新；
- 模拟更高包版本并验证升级路径；
- 更新 README、包级知识和 State；
- 将经验证的长期事实晋升，归档 bootstrap 材料。

**完成证据**：客户端无需 checkout、SSH 密钥和本地构建即可安装、升级和查询包。

## 执行顺序与依赖

```text
阶段 1
  → 阶段 2
  → 阶段 3
  → 阶段 4
  → 阶段 5
  → 阶段 6
  → 阶段 7
```

允许在实现中并行调查 MrRSS 依赖和 GitHub Release API，但正式状态必须按证据推进。任何阶段发现长期设计不成立时，先更新 Design 并请求必要裁决，不用局部补丁掩盖偏移。
