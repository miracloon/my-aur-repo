# 开发文档治理

> Audience: AI and maintainer
> Status: normative

本文件定义阶段性开发材料如何进入、退出和影响当前事实。长期控制文档不保存单包接入进度、短期方案或未验证实现。

## 目录模型

```text
docs/development/
├── DEV_WORKFLOW.md
├── active/
│   └── <initiative>/
└── history/
    └── <initiative>/
```

- `active/` 只保存正在推进的阶段材料，默认同一时间只有一个主要 initiative。
- `history/` 保存已经结束的阶段记录，不是当前实现事实源。
- identifier 使用稳定可辨的主题名；首次建设使用 `bootstrap`。
- initiative 内可按需要包含 `design.md`、`plan.md`、`state.md` 或任务定义，不要求固定文件组合。
- 一次性小任务无需创建阶段目录。

## 信息身份

| 材料 | 回答什么 | 不能证明什么 |
|---|---|---|
| Design | 为什么做、范围、决定与开放问题 | 对应能力已经实现 |
| Plan | 怎样分段推进、依赖和完成证据 | 当前已经执行到哪里 |
| 任务定义 | 单个可执行范围、边界和验收 | 长期项目规范已经改变 |
| State | 已验证完成、进行中、未实现和下一步 | 未引用证据的结论真实有效 |

未决定内容必须保持开放身份。不能为了让方案完整，把候选实现写成长期事实。

## 当前事实优先级

1. 用户当前明确裁定；
2. `AGENTS.md` 的硬约束；
3. 长期控制文档与模块文档；
4. 当前代码、测试、工作流和 Release 运行事实；
5. `active/` 阶段材料；
6. `history/` 追溯材料。

长期文档与实现不一致时，应调查偏移并在同一任务内闭合，不能用活动设计静默覆盖现实。

## 推进规则

- 多步工作在修改前明确范围、边界和验证方式。
- 进入新的独立任务前重新读取相关长期文档和当前 State。
- 承接阶段计划时以其中明确范围为准，对话中的额外想法不自动扩张任务。
- 发生重要设计偏移时先更新 Design 或明确请求用户裁决。
- 结构迁移同步更新引用、schema、测试、自动化和当前文档，不留下双重事实源。
- 不为内部旧结构保留永久兼容层，除非其已经成为明确的客户端契约。

## State 维护

跨上下文、跨执行者或持续探索的工作必须维护 `state.md`。State 只保存：

- 已验证完成；
- 当前进行中；
- 尚未实现或验证；
- 开放问题与新发现；
- 当前下一步；
- 长期治理文档的同步状态。

State 是当前快照，不是逐命令日志。只在语义状态变化时更新。

## 事实晋升

阶段结论只有同时满足以下条件，才进入长期控制文档：

- 已通过代码、测试、Actions 或实际客户端行为验证；
- 阶段结束后仍然成立；
- 属于项目身份、架构、工作流、结构规范或可复用模块知识；
- 不依赖某个包的一次性资产名称、版本或故障。

单包持续知识进入该包 README；短期过程留在阶段材料；当前故障进入 GitHub Issue。未实现能力不得因出现在 Plan 中而写成“已支持”。

## 归档

阶段完成后：

1. 核对交付与 State，清除伪进行中状态；
2. 将经验证且长期成立的事实晋升到控制文档或模块文档；
3. 将包实例知识写回对应包目录；
4. 验证文档链接、schema、测试和正式 Actions；
5. 将整个 initiative 从 `active/` 移入 `history/`。

历史材料统一视为 historical，仅用于追溯决策和回归来源，不参与日常启动上下文。

## 验证原则

- 核心版本比较、配置解析、数据库变换和失败汇总必须有自动化测试。
- 配置、工作流和文档调整执行与风险相称的验证。
- 软件包的正式构建、编译和安装验证只在 GitHub Actions 中进行。
- 未运行的测试、未触发的工作流和未消费的 Release 不得标记为已验证。
