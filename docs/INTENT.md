## 项目定位

`my-aur-repo` 是维护者个人自用的 Arch Linux 软件包供应工程。它补上“上游发布形式无法直接被 pacman 消费”这一段：自动跟踪公开上游，在 GitHub Actions 中打包，并通过同一 GitHub 仓库的公开 Releases 提供 pacman 二进制仓库。

项目服务于维护者自己的 `x86_64` Arch Linux 环境。客户端只消费已经发布的软件包，并由维护者在需要时手工执行正常的 `pacman` 或 `yay` 命令；客户端不承担打包、编译或自动升级职责。

---

## 核心目标

- 将不同上游交付形式统一为可由 pacman 安装和升级的软件包。
- 让上游正常发布新版本时，监控、配方更新、远端打包和发布无需人工介入。
- 以标准 PKGBUILD 保存完整打包事实，使发布内容可审计、可复现、可由 AI 维护。
- 保持配置驱动和薄自动化，复用 Arch 与 GitHub 已有能力，不重造包管理器。
- 让单包故障相互隔离，已有仓库和其他软件包继续可用。

---

## 成功判断

- 启用包的新版本能在每日监控后进入远端构建和发布链路。
- 客户端能从配置好的自定义源直接安装和升级，不在本机执行 PKGBUILD。
- Git 仓库不因上游源码、下载资产或二进制产物而持续膨胀。
- 新的上游监控方式或交付形式可以在稳定边界内扩展，不要求迁移既有包目录。
- AI 能从控制文档、结构化声明和失败 Issue 恢复运维上下文，而无需依赖聊天历史。

## 边界与不做清单

- 不向 AUR 发布，也不承担面向其他用户的支持和公共包维护义务；公开 GitHub 仓库只是自用工程及只读交付端点。
- 不 fork 或二次开发上游。仅做进入 Arch 包所必需的安装路径、桌面集成、依赖声明和轻量修正。
- 不覆盖上游提供的全部系统和架构。项目全局只支持维护者需要的 `x86_64`，架构无关包可以使用 `any`。
- 不在客户端打包或编译；正式构建和安装验证属于 GitHub Actions。
- 不隐式消费 AUR 依赖。必要依赖若不在官方仓库中，应作为独立包显式接入本项目。
- 不公开再分发许可证不允许公开分发的资产。此类软件需要未来独立的私有交付方案，不能降低现有公开仓库边界。
- 不把上游源码、deb、AppImage、压缩包、`.pkg.tar.zst`、仓库数据库或缓存提交进 Git。
- 不为单个案例增加项目级抽象。实例经验只有在可复用并经过运行验证后才晋升为长期能力。
- 不追踪同一上游版本下被静默替换的资产；已识别的版本默认视为不可变。

## 关键设计决策

### 单仓库、双存储面

Git 保存配方、配置、自动化和文档；同一公开 GitHub 仓库的 Release Assets 保存 pacman 数据库与二进制包。Release Assets 不进入 Git 历史，因此无需为二进制另建代码仓库。

### 稳定身份与可变策略分离

包目录只按 pacman 包名组织。Release、tag、commit、deb、AppImage 或源码构建都是可变策略，不进入目录层级；上游改变交付方式时不迁移包身份。

### PKGBUILD-first

PKGBUILD 是 Arch 打包事实源，机器人直接更新并提交其中的版本和校验和。项目不通过运行时模板或自有 DSL 替代标准 PKGBUILD。

### 单一目标架构

全局统一目标为 `x86_64`，不建立多架构矩阵。单包只声明本仓库实际支持和使用的资产，不替上游维护完整平台清单。

### 直接发布但不跳过验证

AI 和自动化可以直接提交与发布，以减少维护者操作；机器验证是直接发布的前置条件，不得因“自用”而绕过。

### 签名是扩展项

初始仓库通过 GitHub HTTPS 交付，不强制 GPG 包签名。发布结构保留未来签名接入位置，但未启用的签名能力不能被描述为现有安全保证。

## 术语与概念澄清

- **AUR**：托管 PKGBUILD 的公共社区服务，不保存本项目的二进制包；本项目不向其发布。
- **pacman 仓库**：`my-aur.db`、`my-aur.files` 与 `.pkg.tar.zst` 构成的可消费制品集合，承载于 GitHub Releases。
- **`-bin`**：表示包使用上游预编译产物，不表示包位于 AUR，也不表示本项目不生成 Arch 包。
- **公开但自用**：任何人可读取仓库和 Release，但项目目标、兼容承诺和维护义务只面向维护者本人。
- **直接发布**：验证通过后不需要人工批准；不等于无验证发布。

## 长期方向

- 按真实包案例逐步增加监控策略和打包能力，不提前实现完整插件框架。
- 稳定的职责位置可以提前写入结构规范；没有真实实现时不创建空目录或伪支持代码。
- 若未来出现不能公开再分发的必要软件，为其增加独立私有交付通道，而不是改变现有公开仓库的含义。
