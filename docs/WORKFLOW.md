## 全链路概览

```text
每日定时 / 手工触发 / 主分支变更
  → 从 registry 读取启用包
  → 按单包 monitor 声明解析当前稳定上游版本
  → 对比 PKGBUILD 期望版本与 Release 中 my-aur.db 的已发布版本
  → 为需要更新的包准备标准 PKGBUILD 变更
  → 各包在独立、一次性的 Arch x86_64 环境中构建和验证
  → 汇总成功包，提交对应文本变更
  → 单一发布任务先上传包、最后更新仓库数据库
  → 失败包保留旧版本并更新其 GitHub Issue
  → 客户端以后通过 pacman 或 yay 手工安装、升级
```

Git 表达期望打包状态，GitHub Release 中的 pacman 数据库表达实际发布状态。Git 版本领先但发布失败时，后续运行以二者差异为依据重试；不得仅凭 Git 中版本相同就假定已经发布。

`yay -S <pkgname>` 会优先查询 pacman 已配置的同步数据库。包若存在于 `[my-aur]`，安装由 pacman 直接下载二进制完成，不访问 AUR，也不在客户端运行 PKGBUILD。

## 运转环节总表

| 环节 | 主要组件 / 文件 | 运行环境 | 输入 | 输出 | 下游影响 |
|---|---|---|---|---|---|
| 触发与选包 | Actions、`registry/packages.toml` | GitHub Actions | 定时、手工或 Push 事件 | 待检查包集合 | 决定监控范围 |
| 上游监控 | 单包 `package.toml`、监控实现 | GitHub Actions | 上游元数据 | 规范化上游版本 | 决定是否准备更新 |
| 版本与配方准备 | `PKGBUILD`、校验和工具 | GitHub Actions | 上游版本和来源 | 候选 PKGBUILD 变更 | 提供确定构建输入 |
| 独立构建 | `makepkg`、临时 Arch 环境 | GitHub Actions | 单包目录和官方/本仓依赖 | `.pkg.tar.zst` | 进入产物验证 |
| 验证与汇总 | 公共验证器、可选包级检查 | GitHub Actions | 候选配方和包 | 成功包、失败报告 | 决定提交与发布集合 |
| Git 状态提交 | GitHub 仓库 | GitHub Actions | 验证成功的文本变更 | 新的期望状态 | 为失败重试和审计提供依据 |
| 仓库发布 | 固定 GitHub Release、`repo-add` | GitHub Actions | 成功包、现有数据库 | 包资产和新数据库 | 客户端可发现新版本 |
| 故障管理 | GitHub Issues | GitHub | 失败摘要和运行链接 | 每包一个活动故障入口 | 供维护者或 AI 修复 |
| 日常消费 | pacman / yay | 维护者客户端 | `[my-aur]` 数据库 | 安装或升级结果 | 完成交付 |

## 环节详解

### 触发与选包

- **目的**：兼顾无人值守检查、即时重试和配方变更验证。
- **触发来源**：每日一次定时检查、可指定包的手工触发、影响包或公共自动化的主分支 Push。
- **选包规则**：只有根清单中显式启用且目录有效的包进入正式流水线。
- **并发边界**：监控和单包构建可以并行；仓库数据库只能由一个发布任务串行修改。
- **保活**：公开仓库长期无提交时，以低频空提交防止 GitHub 自动停用定时工作流；保活不修改项目文件。

### 上游监控

- **目的**：把不同上游发布习惯解析成确定、可比较的版本身份。
- **输入**：单包监控类型、上游位置、稳定版过滤规则和必要的版本规范化规则。
- **输出**：当前稳定上游版本；未注册或无法确定的监控类型直接失败。
- **边界**：同一版本默认不可变；初始能力不因资产内容被替换而自动增加 `pkgrel`。

### 版本与配方准备

- **目的**：让实际构建使用一份标准、完整、可审计的 PKGBUILD。
- **新上游版本**：更新 `pkgver`、将 `pkgrel` 置为 `1`、更新来源校验和。
- **仅打包变化**：保持 `pkgver`，显式增加 `pkgrel`。
- **禁止情况**：候选包版本不大于已发布版本，或配方改变但版本未提升时，不进入发布。

### 独立构建

- **目的**：隔离客户端环境与包间污染。
- **运行位置**：官方 Arch Linux `x86_64` 临时环境中的非 root 构建用户。
- **依赖来源**：Arch 官方仓库及本项目已经发布的包。
- **隔离单位**：每个包独立构建；一个包失败不改变其他包的结果。
- **产物**：只在当前 Actions 运行和发布阶段存在，不提交进 Git。

### 验证与汇总

公共门禁至少覆盖 schema、名称一致性、PKGBUILD 基础规范、来源校验和、构建结果、包元数据、架构、文件布局、`namcap` 和干净环境安装/卸载。

GUI 软件不要求在无桌面环境中强制启动。包级检查可以补充公共门禁，但不能替代公共门禁；不可靠的启动测试不得作为全局要求。

成功包进入提交与发布集合。失败包保持 Git 与 Release 中的旧版本，并输出包含上游版本、失败阶段和运行链接的结构化摘要。

### Git 状态提交

机器人只提交验证成功包的 PKGBUILD 和相关文本变化。提交失败时不发布相应包；提交成功而发布失败时，下一次运行依据 Git 与 pacman 数据库的版本差异重试。

### 仓库发布

- 新包文件先上传并确认可读取，`my-aur.db` 与 `my-aur.files` 最后替换。
- 数据库只索引每个包的当前版本；Release 额外保留上一个包文件用于紧急回退。
- 发布任务不能覆盖相同的完整包版本。
- 具体 Release 结构、客户端契约与签名扩展见 [`modules/repository.md`](modules/repository.md)。

### 故障管理

每个失败包最多维持一个活动 Issue。同一故障再次发生时更新该 Issue，恢复后自动关闭。Issue 是自动化与 AI 的运维交接面，不是长期项目事实源。

### 日常消费

客户端只配置公开 HTTPS 软件源并使用常规 pacman/yay 命令。客户端不需要 GitHub Token、SSH 密钥、源仓库 checkout 或构建工具链。

## 外部依赖与运行环境

| 外部系统 | 在流程中的角色 |
|---|---|
| GitHub 仓库 | 保存公开的配方、自动化、文档和历史 |
| GitHub Actions | 执行每日监控、构建、验证、提交和发布 |
| GitHub Releases | 保存 pacman 数据库和二进制包 |
| GitHub Issues | 保存当前包级故障与 AI 运维入口 |
| 上游发布端点 | 提供版本元数据、源码或预编译资产 |
| Arch 官方仓库 | 提供构建和运行依赖 |
| 维护者客户端 | 通过 pacman/yay 消费已发布包 |

## 开发环节在整体中的位置

包声明、PKGBUILD、自动化和工作流变更先进入 Git，再通过相同的远端构建与验证门禁影响 Release。阶段性 Design、Plan 和 State 只描述建设意图与当前状态，不能单独证明对应能力已经实现；其治理规则见 [`development/DEV_WORKFLOW.md`](development/DEV_WORKFLOW.md)。
