=== 写作指导（本区块不进入最终文档）===

【文档定位】
INTENT.md 是控制面文档矩阵中最核心的意图文件。
它回答"项目为什么存在、边界在哪、为什么这样取舍"——是 AI 理解项目方向的锚点。

【核心职责】
记录项目级的意图、取舍和设计决策。只记录"缺失后会导致 AI 做出错误判断或方向漂移"的信息。

【写作原则】
- 按主题组织，不按对话顺序。以结论为主，背景作为从属说明
- 使用陈述句，不用问答体、聊天体、会议纪要体
- 追求"对 AI 判断有用"，不追求字数或覆盖感
- 没有稳定结论的内容不入正文，标记 【待裁决】 或省略
- 通用成文约束见 output-contract.md，结构约束见 structure-contract.md

【INTENT 专属规则】
- 禁止粘贴实现代码。用自然语言描述设计语义和意图，AI 的检索能力足以从代码库中定位实现。仅在必须精确表达接口边界或类型约束时，允许不超过 2 行的伪代码或类型签名
- 对模块的提及保持"索引级"——一行摘要 + 链接到模块文档。详细设计在模块文档中展开
- 重大架构选择的驱动、取舍和理由留在 INTENT；项目存在 ARCHITECTURE.md 时，逻辑组件、职责、依赖、接口和数据所有权的当前模型归 ARCHITECTURE，不在本文件展开
- 不记录进度状态。INTENT 记录的是意图（"计划支持多语言"），不是进度（"已完成 60%"）
- 唯一允许的标签是 【待裁决】，表示用户尚未确认的结论
- 膨胀时向下推（拆出模块文档），不横向扩（加新栏目）
- 参考体量：50–150 行。超出时检查是否混入了操作步骤、结构细目或模块级细节

【各栏目 放/不放 速查】

| 栏目 | 放什么 | 不放什么 |
|------|-------|---------|
| 项目定位 | 项目是什么、服务谁、解决什么问题 | 实现细节、技术选型过程 |
| 核心目标 | 项目要达成的稳定目标 | 版本计划、任务分解、进度 |
| 成功判断 | "什么算完成/达标"的明确标准 | 测试用例、验收流程 |
| 关键功能/交付形态 | 影响项目方向的功能索引（一行一条） | 功能说明书、API 细节、使用教程——归 MODULE 或 README |
| 边界与不做清单 | 明确不做什么、为什么不做 | 显而易见的排除项（如"不做无关的事"） |
| 关键设计决策 | "为什么选 X 不选 Y"的项目级决策 | 模块内部的局部决策——归 MODULE |
| 术语与概念澄清 | AI 容易误解的术语和概念边界 | 通用技术术语的教科书解释 |
| 长期方向 | 演化意图、已预见的拐点 | 具体排期、版本号、里程碑日期 |

【自检清单】
生成或更新 INTENT.md 后，快速验证：
- [ ] 全文是否在 50–150 行以内？超出了说明可能混入了不该在这里的内容
- [ ] 是否有代码片段？如果有，删除并改用自然语言描述
- [ ] "关键功能"中每条是否只有一行摘要？有没有展开成功能说明书？
- [ ] 是否有进度状态信息（"已完成""进行中"）？应移除
- [ ] 是否有只影响单个模块的局部决策？应移到模块文档
- [ ] 若存在 ARCHITECTURE.md，本文是否只保留架构驱动和取舍理由，没有复制当前组件模型？
- [ ] 可选栏目中，没有内容的是否已删除（而非留空）？
