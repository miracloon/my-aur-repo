=== 写作指导（本区块不进入最终文档）===

【文档定位】
MODULE 文档是主控制文档的纵向延伸——当某个模块的内容量超出主文档
内联阈值时，从主文档拆出为独立文件。它是 INTENT、存在时的 ARCHITECTURE、SPEC 和 WORKFLOW
在模块层级的纵向展开，用“意图 + 结构 + 运转”的三合一视角覆盖单个模块。

【核心职责】
为单个逻辑模块提供完整的控制面信息：为什么存在、如何组织、如何运转。

【写作原则】
- MODULE 文档可以是实质性的——复杂模块的文档可能需要 50-150 行甚至更多
- 粒度对齐 SPEC 的模块划分：一个逻辑模块一份文档，有归纳性
  （不要一个文件一个 MODULE doc，而是一个子系统/逻辑模块一个）
- MODULE 文档中的设计意图应能追溯到 INTENT.md 关键功能索引中的一行
- 通用成文约束见 output-contract.md，结构约束见 structure-contract.md
- 拆分阈值和主文档索引格式见 structure-contract.md 的模块拆分章节

【表达格式偏好】
- 默认使用表格和无序列表直接陈述事实，不要用段落散文复述
- 仅在需要解释设计取舍的因果关系时使用短叙述（2-3 句话封顶）
- 禁止粘贴实现代码。用自然语言描述设计语义和逻辑。
  仅在必须精确表达接口边界或类型约束时，允许不超过 2 行的伪代码或类型签名。
  AI 的检索能力足以从代码库中定位实现，代码复述毫无价值

【膨胀管理】
MODULE 允许水平膨胀（新功能 = 新的 `###` 子节），但需要管控：
- 每个功能/领域用 `###` 组织，顶部内容索引表追踪所有 `###` 主题
- 每个 `###` 保持精炼——用几段话或表格说清要点，不写说明书
- 新功能不是都要进 MODULE：只有影响 AI 理解模块设计方向的才值得记录
- 若单个 `###` 膨胀到独立撑起一份文档，考虑是否该拆出为独立模块

【与主文档的关系】
- INTENT.md "关键功能/交付形态" → 一行索引，链接到本文档
- ARCHITECTURE.md（若存在）→ 定义本模块在全局逻辑组件模型中的职责、依赖和接口边界，本文档展开模块内部细节
- SPEC.md "模块边界与组织方式" → 模块边界规则，链接到本文档
- WORKFLOW.md "环节详解" → 涉及本模块的环节，可链接到本文档

【自检清单】
- [ ] 本文档的模块是否能在 INTENT.md 的功能索引中找到对应的一行？
- [ ] 本文档的粒度是否和 SPEC 的模块划分一致（逻辑模块级，非文件级）？
- [ ] 是否有代码片段？删除并改用语义描述
- [ ] 是否有段落散文复述了代码逻辑？改用表格或列表直接陈述事实
- [ ] 是否有项目级信息混入？应回到主文档
- [ ] 内容索引表是否覆盖了所有 `###` 主题？
- [ ] 可选栏目中，没有内容的是否已删除？
