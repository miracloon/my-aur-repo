# 文档结构治理

> 纯查询手册——在生成、更新或审阅文档结构时查阅。
> 本文件定义控制面文档的全局结构治理策略。各文档专属的栏目定义见对应的 `assets/*.example.md`。

---

## 为什么需要结构治理

AI 在更新文档时，面对"新信息放不进现有栏目"的情况，最自然的反应是新增一个 `##` 标题。这在单次操作中看似合理，但多次累积后会导致：

- 文档结构碎片化，丧失层次感和设计逻辑
- 栏目越界——本应属于另一份文档的内容被塞入了错误的位置
- 结构膨胀不可逆——没有机制触发结构回收或合并

结构治理的核心原则：**`##` 是承重墙，`###` 是隔断墙。** 承重墙的变更需要审批，隔断墙可以自由调整。

初始化完成后，顶层栏目本身就是已确认的治理契约。普通文档优化可以自主调整段落、表格、措辞和 `###` 以下结构，但不能把 `##` 当作纯叙事格式静默改写；只有改变文档职责或结构契约时才申请调整。

---

## 栏目索引表

每份控制文档的顶部应包含栏目索引表，同时承担导航、结构契约、归属判断三个功能：

```markdown
## 栏目索引

| 栏目 | 回答什么 | 不放什么 |
|------|---------|---------|
| {栏目名} | {该栏目收纳什么信息} | {什么信息不应放在这里} |
```

栏目索引表 = 该文档的结构契约。模板（`assets/*.example.md`）为每份文档定义了标准栏目。

### 栏目索引表的作用

| 功能 | 说明 |
|------|------|
| 导航 | 读者快速了解文档包含哪些部分 |
| 结构契约 | 索引表中的栏目即为合法的 `##` 分区 |
| 进入判断 | "回答什么"列帮助判断新信息应归入哪个栏目 |
| 排除判断 | "不放什么"列帮助判断什么内容应去其他文档 |

---

## 分阶段 `##` 结构规则

`##` 栏目的锁定程度随文档生命周期阶段递进：

| 阶段 | `##` 结构规则 | 理由 |
|------|-------------|------|
| **初始化 Phase 3（落骨架）** | 模板为参考，AI 可按需提议增减栏目 | 结构尚在探索，需要灵活性 |
| **初始化 Phase 4（压实）** | 对照模板收束结构，合并碎片栏目，确认最终栏目索引表 | 结构定型的正确时机 |
| **初始化完成后（更新/审阅）** | `##` 结构锁定，变更需用户确认 | 防止结构退化 |

- `###` 及以下层级不受锁定约束，可在栏目内自由组织

---

## 模块拆分（纵向深度控制）

栏目锁定控制的是文档的**横向宽度**（栏目数量），模块拆分控制的是**纵向深度**（单栏目内容量）。两者共同维护文档的结构健康度。

### 拆分阈值

以下为参考默认值，用于触发拆分判断，不是脱离语义的硬切线。实际是否创建模块文档仍由职责和维护边界决定：
| 模块内容量 | 默认处理 |
|-----------|---------|
| ≤ 10 行 | 优先内联到主文档对应栏目 |
| > 10 行 | 优先考虑拆出 `docs/modules/{name}.md`，主文档保留摘要 + 链接 |

超过阈值但没有独立模块职责、拆分会割裂同一判断或制造重复事实源时可以继续内联；内容虽短但已经形成独立加载、事实权或维护边界时也可以拆分。偏离默认值时说明结构理由，不按行数机械执行。

### 主文档中的模块索引

当模块级内容存在时，在主文档对应栏目中使用索引表：

```markdown
### 模块设计索引

| 模块 | 核心设计意图 | 关键约束 | 详情 |
|------|------------|---------|------|
| auth | JWT 无状态认证 | 禁止 session | [→ docs/modules/auth.md] |
| config | TOML→DB 同步 | 启动时 seed | 内联（量少） |
```

## 新信息的归属路由

当需要将新信息写入文档时，按以下顺序判断：

1. **文档间路由**：这条信息属于哪份文档？→ 参考 [matrix-boundaries.md](matrix-boundaries.md)
2. **栏目内路由**：属于该文档的哪个 `##` 栏目？→ 查看栏目索引表的"回答什么"列
3. **若无匹配栏目**：先重新检查是否归属错了文档；若确实属于本文档，提交结构变更申请
4. **若栏目已过深**：单个栏目内容量超出阈值时，考虑拆出模块文档

---

## 结构变更申请

初始化完成后，若 AI 判断需要新增或调整 `##` 栏目，应提交具体方案供用户裁决，而不是问开放式问题：

```markdown
### 结构变更申请

**申请类型**：新增栏目 / 合并栏目 / 拆分栏目
**目标文档**：{INTENT.md / SPEC.md / ...}
**具体方案**：{新栏目名称、位置、收纳什么信息}
**理由**：{为什么现有栏目无法容纳这条信息}
**影响**：{对栏目索引表和其他文档的影响}
```

**禁止**：
- 未经用户确认直接新增 `##` 栏目
- 问"需要我加一个栏目吗？"这类没有具体方案的开放式问题
