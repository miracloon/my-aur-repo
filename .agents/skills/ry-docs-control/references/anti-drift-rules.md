# 权威来源与防漂移规则

本文用于判断不同来源各自能证明什么、冲突怎样处理，以及哪些信息可以进入长期治理正文。

---

## 按问题选择权威

不同问题使用不同权威，不建立覆盖一切的单一来源优先级：

| 问题 | 主要权威 | 不能自动证明什么 |
|------|---------|----------------|
| 用户希望项目达成什么、怎样取舍 | 用户当前明确裁定、已经确认的 INTENT | 不证明已经实现 |
| 项目当前实际怎样运行 | 代码、配置、测试、构建结果、日志和可重复观察 | 不证明这种现状符合用户意图或应长期保持 |
| 项目长期怎样理解和维护 | 已确认的控制面正文及用户当前裁定 | 文档可能漂移，不能覆盖相反的实现证据 |
| 当前开发做到哪里 | State 与其引用的实现、验证证据 | 不替代未来计划或长期治理结论 |
| 阶段设计和执行边界是什么 | Design、Plan、任务定义，各自在自身信息身份内生效 | 不证明完成或验证 |
| 源码、文档或资产应改哪一份 | 已确认的当前维护源、生成定义 | 安装副本、历史稿和派生副本不自动取得事实权 |
| 平台支持什么、格式怎样 | 官方规范、官方实现与目标环境实测 | 不由模板或模型常识补全 |
| 跨项目默认偏好是什么 | `AI_GLOBAL_PREFS.md` | 项目当前明确裁定可以改变其适用结果 |

用户当前明确裁定拥有意图与治理取舍的最终权，但不能把“用户希望如此”直接写成“项目已经如此”。同样，代码和运行现实可以证明当前实现，却不能独自决定它应成为长期规范。

## 处理来源冲突

来源不一致时先说明冲突属于哪一种关系：

- **意图与实现不同**：确认是实现尚未完成、代码发生漂移，还是长期文档已经失效；不自动改写任一方。
- **长期文档与运行现实不同**：把文档陈述和可观察事实并列呈现，由用户决定更新文档还是另开开发任务修正实现。
- **阶段材料与实现不同**：保持 Design、Plan、State 和代码各自身份；计划、候选和状态声明不能冒充实现证据。
- **多个文档竞争同一事实**：确定唯一正文，其他位置改为摘要、链接或删除。
- **全局偏好与项目需求不同**：普通偏好由已确认项目需求覆盖；硬性约束冲突交给用户明确裁决。

冲突解决后同步修正受影响的当前正文，不保留互相竞争的旧结论。

## 禁止行为清单

| # | 禁止行为 |
|---|---------|
| 1 | 补写用户未表达的目标、边界或长期方向 |
| 2 | 把当前代码结构直接升级为 SPEC、WORKFLOW、ARCHITECTURE 或 INTENT 的规范结论 |
| 3 | 把探索性讨论、计划步骤或 State 声明写成已完成事实 |
| 4 | 让入口文档 AGENTS 替代核心文档承担完整正文 |
| 5 | 把“模板有栏目”误当成“栏目现在就应该写满” |
| 6 | 把提问退化成流水账式信息收集，或要求用户重复确认已经明确授权的行动 |
| 7 | 遇到文档与代码不一致时按固定优先级静默选择一方 |
| 8 | 为了快速完成而跳过会改变目标、事实权或文档职责的关键裁决 |
| 9 | 一次性抛出大量无层次的问题 |
